## 1. 系统概述与总体架构

### 1.1 系统定位

InterviewerAgent 是一个 AI 面试官 Agent 系统：求职者上传简历后，系统自动解析其中的公司经历、项目细节与博客/GitHub 链接，并借助联网检索核实与扩展这些信息；随后 Agent 模拟真实面试官，针对用户的 GitHub 项目深挖技术选型与实现细节，追问技术栈底层原理，并对简历中的夸大表述与逻辑漏洞发起挑战式提问；<u>面试结束后输出多维度评估报告与改进建议。</u>

系统综合运用四项核心技术（课程要求的技术点，均有落地章节）：

| 技术点              | 落地位置                          |
| ---------------- | ----------------------------- |
| 提示工程             | §3.3 面试官人设与五阶段提示词体系           |
| Function Calling | §3.2 联网核实 ReAct Agent 与 4 个工具 |
| 网页信息抽取           | §3.1 简历文件解析 + §3.2 博客正文抓取     |
| 记忆管理             | §3.3 长期档案注入 + 短期对话历史 + DB 持久化 |

### 1.4 总体数据流

```
上传简历(pdf/docx/txt/md)
  → M1: 抽取文本 → ① 简历解析: LLM 结构化提取 ResumeProfile → 可编辑画像表单
  → <font color=red>用户确认画像</font>
  → ② 联网核实(后台任务): ReAct Agent 调 GitHub/搜索/博客工具

  → 报告页: 雷达图 + 引文卡片 + 打印导出
```

**版本策略**：以 lockfile（`uv.lock` 固定版本 / `package-lock.json`）锁定为准，文档记录锁定快照，避免依赖漂移。Python 侧统一用 `uv` 管理环境（`uv sync` 还原依赖），与仓库中已有的 `pyproject.toml` / `uv.lock` 保持一致。

**配置外置**：模型名、`base_url`、API Key、数据库连接串**一律不硬编码**，统一由 `config.py`（pydantic-settings）从 `.env` 读取。换模型 / 换供应商 / 换库只改 `.env`，代码零改动——这也是下文多处"改环境变量即可"说法的前提。

**关键选型论证——POST 流式 vs WebSocket**：v1 曾选 WebSocket（双向通道）。v2 改为**普通 POST + 响应体流式读取（NDJSON 事件流）**：候选人每次回答 = 一次独立 POST 请求，响应体即面试官回复的 token 流；跳过阶段/结束面试等控制指令是低频操作，走普通 REST 即可，无需常驻双向通道。此模式已在参照项目中验证（`fetch` + `response.body.getReader()` 循环），省去 WS 网关、心跳、帧协议、断线重连的全部复杂度；且 HTTP 流对代理/防火墙的兼容性天然更好。

**成本与时延估算**（答辩常问，按单场面试 11 轮问答估算）：

| 环节 | token 量级 | 时延 | 成本 |
|---|---|---|---|
| 简历解析（1 次结构化提取） | 入 ~3K / 出 ~1K | 3~6s | < $0.001 |
| 联网核实（ReAct ≤12 轮工具调用） | 累计入 ~40K / 出 ~3K | 30~90s（后台，用户看进度条） | ~$0.008 |
| 面试问答（11 轮，历史每轮重发） | 累计入 ~250K / 出 ~10K | 首 token 1~2s，整轮 5~15s | ~$0.045 |
| 评估报告（1 次） | 入 ~15K / 出 ~3K | 10~20s | ~$0.004 |
| **单场合计** | — | 用户实际等待 ≈ 11 × 首 token + 报告 | **约 $0.06（不足 0.5 元）** |

结论：成本可忽略（对照 §2 的 $0.15/$0.6 每百万 tokens 单价），主要成本是**联网核实的 30~90s 后台时间**，因此它必须异步且在向导第 3 步用进度轮询承接——这是"先核实后面试"流程设计的直接原因。历史全量重发使 token 随轮数平方增长，但 11 轮 × 1M 窗口远未触顶，无需压缩。

## 3. 核心流程设计

### 3.1 简历解析链路（模块 M1 + M3）

```
[上传] POST /api/v1/resumes（multipart，≤10MB，白名单 .pdf/.docx/.txt/.md）
  → 落盘 uploads/{uuid}{ext}，resumes 表登记 status=parsing
[抽取] PyMuPDF(.pdf) / python-docx(.docx) / 直接读取(.txt/.md) → raw_text
  → 纯文本 < 300 字符 → 判定疑似扫描件 → status=needs_manual
  → 前端向导第2步提示手工补录（人工兜底，链路不阻塞）
[链接抽取] 正则匹配 github.com/{owner}/{repo} 与博客 URL（不依赖 LLM，防漏抽）
[结构化提取] ChatOpenAI(model=settings.LLM_MODEL, temperature=0)
  .with_structured_output(ResumeProfile)
  → 一次调用提取全部字段
[交叉合并] LLM 结果与正则链接结果合并去重；时间线重叠/空字段记入 warnings
[落库] profile_json 存 resumes 表，status=parsed
[人工确认] 向导第2步展示可编辑画像表单 → PUT /api/v1/resumes/{id}/profile
  → status=confirmed，触发联网核实（后台任务）
```

**数据契约 `ResumeProfile`**（Pydantic，与前端 TypeScript 类型镜像）：

```
basics          { name, position, email }
work_experiences[ { company, role, start, end, highlights[] } ]
projects[       { name, github_url, repo_owner?, repo_name?, tech_stack[], role, claims[] } ]
skills          [ str ]
links           { github_urls[], blog_urls[] }
```

其中 **`projects[].claims[]`** 存放候选人自己的断言原话（如"独立设计秒杀系统，QPS 5 万"、"主导开发"），是后续证据比对与挑战式提问的靶子——这是全系统"挑战提问有据可依"的源头。

### 3.2 联网核实链路（模块 M2，Function Calling 落地）

**编排方式**：LangChain 1.x 预置 `create_agent`（ReAct 循环：LLM 决定调用哪个工具 → 执行 → 结果回填 → 直到产出最终答案）。核实任务目标明确、无人在场、无需流式，是 ReAct 的标准场景。

**工具清单**（4 个 LangChain `@tool`，参数用 Pydantic 描述）：

| 工具                             | 实现                                                                                                                                                   | 用途                     |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------- |
| `get_repo_info(owner, repo)`   | httpx 并行调 3 个 GitHub API：`/repos/{o}/{r}`（stars/描述/最后推送）、`/repos/{o}/{r}/languages`（语言构成）、`/repos/{o}/{r}/commits?per_page=100`（近 100 次提交的作者分布），合并返回 | 验证仓库真实性、技术栈构成、是否"主导开发" |
| `get_repo_readme(owner, repo)` | `GET /repos/{o}/{r}/readme`（Accept: raw），截断至约 2K 字符                                                                                                  | 了解项目实际功能与技术叙述          |
| `web_search(query)`            | Tavily（`langchain-tavily`），top 5                                                                                                                     | 核实公司真实性/规模、候选人公开事迹     |
| `fetch_webpage(url)`           | httpx 抓取 + 简易正文抽取（去 script/style 后取正文密度最高的容器），截断                                                                                                     | 抓取博客文章内容               |

**执行流程**（FastAPI BackgroundTasks，无人在场）：

```
[触发] 画像确认后
[Agent 任务] system: "你是背景调查员…" + 简历画像 + 指令:
   "对每个 project 的 claims 逐条核实；公司经历用搜索核实；
    最后输出证据卡列表与风险标记"
[约束] 工具调用轮数上限 12（防失控）；GitHub 请求 10s 超时；404 = 证据卡记 unreachable
[超时] 整个核实任务硬超时 120s，超时即以已获得的部分证据落库，状态置 partial
[产物] EvidenceCard[] + RiskFlag[] → evidence_json / risk_flags_json 落库
       research_status: running → done / partial（部分来源不可达/超时）/ failed
[恢复] 启动时（lifespan）扫描 research_status=running 且 updated_at 早于 5 分钟前的记录，
       置 failed 并允许前端点击"重新核实"重跑——进程被杀/热重载后不留假 running
```

**数据契约**：

```
EvidenceCard { claim, source_type(github/web/blog), source_url, excerpt, 
               verdict(verified|contradicted|suspicious|unverifiable|unreachable) }
RiskFlag     { claim, severity(high|medium|low), evidence_card 引用, note }
```

示例产物：`{claim: "主导开发秒杀系统", verdict: "suspicious", note: "近100次提交中候选人账号仅占2次"}`、`{claim: "QPS 5万", verdict: "unverifiable", note: "仓库无压测代码与数据"}`、`{claim: "GitHub 仓库 interview-agent", verdict: "contradicted", note: "仓库 404 或私有"}`。

### 3.3 面试引擎（模块 M3，系统核心）

#### 3.3.1 五阶段状态机

| 阶段               | 目标                                        | 默认题数 | 迁移条件          |
| ---------------- | ----------------------------------------- | ---- | ------------- |
| `opening`        | 开场、自我介绍                                   | 1    | 收到自我介绍 → 下一阶段 |
| `deep_dive`      | 项目 STAR 深挖：角色边界、架构决策、最难的问题、技术取舍           | 3    | 题数用尽 或 用户跳过   |
| `tech_principle` | 沿项目技术栈下钻底层原理（如"你提到用 Redis 缓存，说说跳表和持久化策略"） | 3    | 题数用尽 或 用户跳过   |
| `challenge`      | 依据 RiskFlag 逐条发起证据锚定的挑战式提问                | 3    | 红旗过完 或 用户跳过   |
| `wrapup`         | 候选人反问、礼貌收尾                                | 1    | → 触发评估报告      |

**阶段迁移 = 纯 Python 代码**（计数器 + 用户控制指令），状态存 sessions 表的 `phase` 字段。LLM 只负责在当前阶段内生成提问，不负责阶段决策——可测试、可回放，是测试计划文档中状态迁移表驱动测试的直接对象。

#### 3.3.2 单轮处理流程（NDJSON 事件流）

候选人每提交一次回答 = 一次 `POST /api/v1/interview/stream`（请求体 `{session_id, content, client_msg_id}`）。FastAPI 以 `StreamingResponse` 返回 **NDJSON 事件流**——响应体每行一个 JSON 对象，前端 `fetch` + `getReader()` 逐行读取（与参照项目 `streamChat` 模式一致，仅增加按行解析）：

```
候选人提交回答
  → 幂等检查: messages 表 UNIQUE(session_id, client_msg_id)
      命中 → 该轮已处理过（重试/双击），不再生成，直接按消息 id 返回既有结果
      未命中 → 继续
  → 并发检查: 若本会话正处于"生成中"（见下），返回 409，前端提示"面试官正在回复"
  → 消息落库 messages 表 → 状态机判定（迁移则先产出 phase 事件）
      状态机同时算出本轮的 question_no，并把「本阶段已问过的问题」列表取出
  → 组装 prompt:
       system = 人设(固定) + 档案摘要 dossier(画像+证据卡+风险标记, 确认时生成一次)
                + 当前阶段指令模板 + 难度档位
                + "本阶段已问过的题目" 列表（防重复提问）
                + [challenge 阶段] 本轮 RiskFlag 注入("针对此断言、依据此证据质疑")
       history = 全量对话历史（1M 窗口内免压缩）
  → ChatOpenAI.astream() 流式生成
  → 逐 token 产出 {"type":"token"} 事件行
  → 完整消息落库（含 phase / evidence_refs），产出 {"type":"done"} 事件行
```

**并发与时序**：`interview_sessions` 上维护"生成中"标记——生成开始置位、`done` 或异常时复位（异常路径务必 `finally` 复位，否则会话卡死）。生成期间 `POST /skip`、`POST /finish` 一律返回 409，前端据此置灰按钮。同一轮内的"消息落库 + phase/question_count 更新 + 标记置位"放在一个事务里提交，避免候选人消息落了库但状态没走。

**防重复提问**：只靠全量 history 不足以让 LLM 意识到"这个题本阶段已经问过了"，阶段指令里显式带上已问题目列表（从 `messages` 按 `session_id + phase` 过滤即得，无需新表），人设中另加一条"不得重复上一轮已问过的问题"。

事件类型定义见 §5.2。challenge 阶段的**证据锚点由代码注入**（RiskFlag → prompt），LLM 无需也不允许自行引用来源——UI 上的"依据证据"角标直接读代码注入的 evidence_refs，从机制上杜绝面试官虚构仓库细节。

#### 3.3.3 提示词体系（提示工程落地）

`prompts.py` 常量集合（版本化，课程文档可直接引用）：

- **人设**：资深技术面试官，专业、严谨但不羞辱；每次只问**一个**问题；先简短承接候选人上一回答，再提出下一问；不重复上一轮已问过的问题；输出 markdown。
- **阶段指令 ×5**：`opening`（引导自我介绍，聚焦最近项目）/ `deep_dive`（STAR 追问：角色边界、决策动机、困难与解决）/ `tech_principle`（沿候选人提及的技术栈下钻原理，按其使用深度递进）/ `challenge`（依据注入的证据发起质疑，语气是求证而非指控，给候选人解释空间）/ `wrapup`（邀请反问、告知后续流程）。`deep_dive` 与 `challenge` 附 few-shot 示例。
- **难度档位 ×2**（对应 `interview_sessions.difficulty`，避免该字段悬空）：`normal`——追问 1 层，候选人答不上来给提示并放过；`hard`——追问 2~3 层，不主动给提示，答不上来记为观察点在报告中标出。
- **防幻觉硬约束**（人设中）："质疑所依据的事实只能来自给你的证据卡内容，不得虚构仓库细节、数据或经历。"

#### 3.3.4 记忆管理（README 技术点落地）

| 记忆类型 | 内容                     | 实现                                                    |
| ---- | ---------------------- | ----------------------------------------------------- |
| 长期记忆 | 候选人档案（画像 + 证据卡 + 风险标记） | 画像确认后生成 dossier 摘要，注入 system prompt，全程不变              |
| 短期记忆 | 面试对话历史                 | 全量历史直接拼接（1M 上下文使压缩失去必要性）                              |
| 持久化  | 全部消息、阶段状态              | messages / sessions 表；刷新或断线后 `GET messages` REST 回放恢复 |

会话标识：`session_id`（即数据库主键）由前端存 localStorage 并随请求携带。

### 3.4 评估报告链路（模块 M3）

```
[触发] 用户点"结束面试" 或 wrapup 完成 → POST /api/v1/sessions/{id}/finish
[读取] 从 messages 表读全量 transcript（不依赖对话上下文）
[生成] ChatOpenAI(temperature=0.2).with_structured_output(InterviewReport)
       单次调用（课设规模 transcript 约 1~2 万 token，远在 1M 窗口内，无分段摘要分支）
[落库] interview_reports 表 → 报告页渲染
```

**数据契约 `InterviewReport`**：

```
overall_score       0-100
dimensions[5]       { name(表达清晰度|技术深度|项目真实性|问题拆解|学习潜力),
                      score(0-10), comment, quotes[message_id] }
highlight_answers[] 表现好的问答对（quotes[message_id]）
risk_answers[]      暴露问题的问答对（quotes[message_id]）
improvement_plan[]  { problem, action, priority(high|medium|low) }
summary             总评段落
```

**引文锚定（硬校验）**：LLM **只输出 `message_id`**，不自己抄写原文——代码拿 `message_id` 去 `messages` 表取 `content`，按需截取片段渲染成引文块。这样引文天然不会幻觉、不需要"子串匹配 + 失败重试"那套脆弱逻辑（LLM 几乎不可能逐字复现长句，靠子串校验必然频繁失败）。校验退化为一步：`message_id` 必须属于本会话，不属于则丢弃该维度引文并记 warning，不影响报告整体产出。

## 4. 数据库设计

**MySQL 选型与部署**：团队统一 MySQL 8，成员本机开发环境一致，避免"我这跑得通"的协作摩擦；InnoDB 提供真正的事务，支撑 §3.3.2 里"消息落库 + 状态更新"的原子提交（这是并发正确性的前提，SQLite 的写锁模型做不到）。连接串走 `config.py` 的 `DATABASE_URL`，SQLAlchemy 同一套模型换库只改这一行。

演示环境用 Docker 起库，一条命令（写入 README 与答辩脚本）：

```bash
docker run -d --name ia-mysql -p 3306:3306 \
  -e MYSQL_ROOT_PASSWORD=ia123456 -e MYSQL_DATABASE=intervieweragent \
  -e MYSQL_ROOT_HOST=% mysql:8.0 \
  --character-set-server=utf8mb4 --collation-server=utf8mb4_unicode_ci
```

建表沿用 `Base.metadata.create_all`（课设无需 Alembic 迁移）；字符集统一 `utf8mb4`（简历含中文与 emoji），存储引擎 InnoDB。JSON 字段用 MySQL 原生 `JSON` 类型，读取模式固定，不做 JSON 路径查询。

**4 张业务表**（`models/`，`Base.metadata.create_all` 建表）：

| 表                    | 字段                                                                                                                                                                                                                                                                                                | 说明                                              |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| `resumes`            | id PK, filename, file_path, raw_text, status(parsing/parsed/needs_manual/confirmed/failed), profile_json, evidence_json, risk_flags_json, research_status(pending/running/done/partial/failed), warnings_json, created_at, updated_at                                                              | 简历全生命周期；证据卡/风险标记以 JSON 列存储（读取模式固定，无需拆表）；`updated_at` 供启动时重置僵尸 running 用 |
| `interview_sessions` | id PK, resume_id FK, position, difficulty(normal/hard), phase(opening/deep_dive/tech_principle/challenge/wrapup), question_count, status(running/finished/aborted), generating(bool, 生成中标记), started_at, ended_at                                                                             | 面试状态机持久化；phase+question_count 即可完整恢复现场；`generating` 用于 skip/finish 的并发互斥 |
| `messages`           | id PK, session_id FK, client_msg_id(候选人消息的幂等键，面试官消息为 NULL), role(interviewer/candidate), content, phase, evidence_refs_json, created_at，**UNIQUE(session_id, client_msg_id)**                                                                                                       | transcript；候选人与面试官消息均先落库；唯一键保证重试不产生重复消息与重复提问 |
| `interview_reports`  | id PK, session_id FK UNIQUE, report_json, overall_score, created_at                                                                                                                                                                                                                                | 一场会话一份报告                                        |

**状态字段的单一职责**：`phase` 只表示面试所处的**阶段**（五个值），"这场面试结束了"由 `status=finished` 表达——v2 早期把 `finished` 塞进 `phase` 会造成两套终态语义，状态迁移表会出现歧义。阶段迁移表（§7 测试对象）以 `status=running` 为前提，`phase` 在其内部单向迁移至 `wrapup` 为止。

**ER 关系**：`resumes 1─N interview_sessions 1─N messages`；`interview_sessions 1─1 interview_reports`。

**隐私处理**：简历含手机号/邮箱等个人信息。约定：仅存本地 MySQL，不外传第三方（联网核实只发送**仓库名、博客 URL、公司名**等公开检索词，不发送手机号/邮箱/整份简历）；`uploads/` 文件名用 uuid 不保留原始文件名；提供 `DELETE /api/v1/sessions/{id}` 与 `DELETE /api/v1/resumes/{id}` 级联删除接口，答辩时作为"数据可清除"的说明点。

### 5.2 流式接口：`POST /api/v1/interview/stream`

请求体：`{"session_id": "...", "content": "候选人回答…", "client_msg_id": "前端生成的 uuid"}`

`client_msg_id` 是幂等键：前端每次发送生成一个 uuid 并随消息一起存本地；超时重试、断线重发、误点两次发送都携带同一个 uuid，服务端据此识别为同一轮，不重复写入也不重复生成（见 §3.3.2）。

响应：`StreamingResponse`（`media_type="application/x-ndjson"`），**每行一个 JSON 事件**：

```json
{"type": "phase", "phase": "challenge", "question_no": 8}
{"type": "token", "content": "…"}
{"type": "token", "content": "…"}
{"type": "done", "message_id": 42, "evidence_refs": [3]}
{"type": "interview_ended"}
{"type": "error", "code": "LLM_TIMEOUT", "retriable": true}
```

事件语义：`phase`（阶段迁移，前端驱动步骤条，出现在流首部）→ 若干 `token`（流式片段）→ `done`（本条消息完成落库；challenge 阶段携带证据引用）→ `interview_ended`（wrapup 完成，前端转轮询报告）或 `error`。

**可靠性设计**：候选人消息**先落库再进引擎**（请求到达即持久化，与流是否中断无关）；`client_msg_id` 唯一键保证重复请求只生效一次（幂等由键保证，而非"每轮独立 POST"这个形式本身）；流中断（网络/刷新）时已生成内容的安全恢复 = 重新打开页面 → `GET messages` 回放历史 → 继续下一轮——无连接状态需要维护，这正是无状态 POST 流式优于常驻连接的地方。

**前端读取模式**（与参照项目 `streamChat` 一致）：`fetch` POST → `response.body.getReader()` 循环 → `TextDecoder` 解码 → 按换行符切分逐行 `JSON.parse` 分发事件。

## 8. 风险与对策

| #   | 风险                                         | 对策                                                                                              |
| --- | ------------------------------------------ | ----------------------------------------------------------------------------------------------- |
| 1   | **GitHub API 限流**：未认证 60 次/h，一轮核实约耗 6~10 次 | `GITHUB_TOKEN` 环境变量（5000 次/h）；证据卡落库即缓存，同一简历二次面试零重复请求                                            |
| 2   | **国内网络**：GitHub/Tavily 间歇不可达               | 代理环境变量可配；搜索可切博查（Bocha）；**优雅降级**：来源不可达时证据卡记 `unreachable`，面试自动切"仅基于简历"模式并在 UI 明示——降级设计写入文档作为答辩亮点 |
| 3   | **面试官幻觉**：虚构仓库细节，质疑反被戳穿                    | 三重防线：只有证据卡内容可入 prompt；challenge 阶段证据由代码注入（非 LLM 自选）；人设硬约束 + 报告引文由 `message_id` 回查真实消息（不靠 LLM 抄原文）       |
| 4   | **流中断**（网络抖动/用户刷新）                         | 消息先落库；恢复 = 重开页面 `GET messages` 回放历史，无连接状态需恢复；重复请求由 `client_msg_id` 唯一键挡掉                            |
| 5   | **首 token 延迟**（长 prompt + 生成）              | 流式输出（用户感知延迟 = 首 token 时间）；前端"面试官正在思考…"占位；dossier 一次性生成不重复计算                                     |
| 6   | **扫描件/复杂排版 PDF 解析失败**                      | 文本长度阈值检测 → `needs_manual` 状态 → 向导第 2 步人工补录画像（流程天然兜底）                                            |
| 7   | **结构化输出偶发不合规**                             | Pydantic 校验失败重试 1 次（温度 0→0.3）+ 兜底默认值 + warnings 上报前端                                            |
| 8   | **静态导出路由限制**                               | `output: "export"` 不支持运行时动态路由 → 页面参数统一用查询参数 + `useSearchParams`（已定约定，见 §6）                      |
| 9   | **后台核实任务丢失**：进程被杀/热重载导致 `research_status` 永停 `running`，前端无限轮询 | 任务硬超时 120s 落 `partial`；启动时（lifespan）扫描超 5 分钟仍在 `running` 的记录置 `failed` 并提供"重新核实"入口    |
| 10  | **并发操作**：流式生成未结束时点跳过/结束，导致阶段与计数错乱           | `generating` 标记互斥，生成期间 skip/finish/stream 返回 409；"落库+状态更新+置位"单事务提交                            |
| 11  | **MySQL 环境不一致**：成员本机无库或版本/字符集不同            | 统一 Docker 起库命令写入 README；连接串走 `.env`；`utf8mb4` 建库；启动时连接失败给出明确报错与修复提示                             |
