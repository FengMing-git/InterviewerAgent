## 1. 一图看懂整体架构

```
┌─────────────────────────┐
│  浏览器（前端页面）        │  Next.js 静态页面（HTML/JS/CSS）
│  登录页 / 新建 / 准备 / 首页│
└───────────┬─────────────┘
            │  HTTP 请求（JSON 为主）
            ▼
┌─────────────────────────┐
│  FastAPI 后端 (api/)      │  ← 「前台接待」：鉴权、参数校验、返回 JSON
│  /api/v1/interviews 等   │
└───────────┬─────────────┘
            │  调用
            ▼
┌─────────────────────────┐      ┌──────────────┐
│  业务服务 (services/)     │ ───▶ │ MySQL 数据库  │
│  简历解析 / 项目分析 …     │      │ 3 张表       │
└───────┬─────────┬───────┘      └──────────────┘
        │         │
        ▼         ▼
   LLM 大模型   GitHub API
  (agent/llm)  (agent/tools)
```

一句话分工：

- **前端**：只负责「展示和交互」。用户看到的所有页面，全是前端代码。
- **后端 (api/)**：只负责「接待」。检查你登录没有、参数对不对，然后叫业务层干活。
- **业务服务 (services/)**：真正干活的人。解析简历、分析仓库、（以后的）核验、面试流程。
- **agent/**：对接外部世界的适配层——大模型（llm.py）和 GitHub（tools/github.py）。
- **数据库 (MySQL)**：所有持久化数据。用 SQLAlchemy（ORM）读写，不手写 SQL。

> **ORM 是什么**：把数据库的表变成 Python 类。`Interview` 类对应 `interviews` 表，
> `db.get(Interview, 3)` 等价于 `SELECT * FROM interviews WHERE id=3`，但拿到的是 Python 对象，
> 改属性再 `db.commit()` 就自动生成 UPDATE 语句。

## 3. 后端是怎么跑起来的（FastAPI 速成）

### 3.1 FastAPI 的核心心智模型

FastAPI 里一切皆「**路由函数**」：一个 Python 函数，绑定一个网址。浏览器请求这个网址，
FastAPI 就调用这个函数，把返回值变成 JSON 发回去。

```python
# backend/app/api/interviews.py（节选）
@router.get("/{interview_id}", response_model=InterviewDetail)   # ← 绑定 GET /interviews/123
def get_interview(
    interview: Interview = Depends(get_owned_interview),        # ← 依赖注入，见 3.3
) -> InterviewDetail:
    return _detail(interview)   # ← 返回 Pydantic 对象，FastAPI 自动转成 JSON
```

三个 FastAPI 特性贯穿全项目，理解它们就理解了 80% 的后端代码：

| 特性 | 一句话解释 | 在本项目里干嘛 |
| --- | --- | --- |
| **路径装饰器** | `@router.get("/xx")` 把函数变成接口 | 每个接口一行 |
| **Pydantic 模型** | 用类声明数据长什么样，自动校验 | 请求体校验（不合法直接 400）、数据库 JSON 列的读写契约 |
| **依赖注入 `Depends`** | 参数里写 `Depends(某函数)`，FastAPI 自动先执行它 | 鉴权：`user = Depends(get_current_user)`，没登录直接 401，函数体里只管写业务 |

### 3.2 以「上传简历」为例，一次请求的完整旅程

用户在新建页点了「上传并开始解析」，前端发出 `POST /api/v1/interviews`（带文件和仓库地址）：

```
① main.py：请求路径带 /api/v1 前缀 → 命中 interviews 路由
② api/interviews.py:create_interview()
   ├─ 依赖注入先跑：get_current_user() 解析 JWT → 查出用户，失败抛 40101
   ├─ 校验文件后缀（不合法抛 40001）、大小（超 10MB 抛 40002）、仓库地址（抛 40000）
   ├─ storage.save_resume()：文件存到 uploads/{随机名}.pdf
   ├─ 建 Interview 数据库记录（status=preparing）
   ├─ background_tasks.add_task(run_preparation_tasks, id)  ← ★ 见 3.4
   └─ 返回 202 {"id": 3, "status": "preparing"}   ← 此刻就返回了，不等解析完成！
③ 后台（响应发出后才执行）：run_preparation_tasks(id)
   ├─ 开两个线程并行：
   │   ├─ run_parse()   → 抽文本 → 调 LLM → 画像 D1 存进 interviews.profile
   │   └─ run_analysis()→ 查 GitHub → 调 LLM → D2 存进 interviews.project_reports
   └─ 都成功后把 status 改成 awaiting_confirm
④ 前端 /prepare 页每 2 秒 GET /interviews/{id} 轮询，看到任务状态变化就刷新界面
```

为什么这么设计？解析要 30~60 秒，如果同步等，HTTP 请求早超时了。所以：
**接口立刻返回 202「已受理」，活儿扔给后台，前端靠轮询看进度**——这就是本项目所有耗时任务（解析/分析/以后的核验和报告）的统一套路。

### 3.3 依赖注入：一行代码完成「鉴权 + 归属校验」

```python
def get_owned_interview(interview_id: int, user=Depends(get_current_user), db=...):
    interview = db.get(Interview, interview_id)
    if interview is None:
        raise AppError(NOT_FOUND, "面试不存在", status=404)      # 40401
    if interview.user_id != user.id:
        raise AppError(FORBIDDEN, "无权访问该面试", status=403)  # 40301
    return interview
```

任何接口只要参数里写 `Depends(get_owned_interview)`，就自动获得了：
登录校验 → 存在性校验 → **只能访问自己的面试**。三个安全检查，一行搞定。

### 3.4 BackgroundTasks 与「自己的会话」

FastAPI 的 `BackgroundTasks` 在**响应发送之后**执行函数。后台任务不能复用请求的数据库
会话（请求已结束），所以每个任务函数都用 `task_session()` 自己开一个——这是
`services/tasks.py` 存在的原因：把「开会话、写状态、记警告、并行、推进状态」这些
每个任务都要做的杂事收敛成公共函数，业务代码只写核心逻辑。

### 3.5 错误处理：业务代码只管抛异常

任何地方 `raise AppError(40003, "PDF 是扫描件…", status=400)`，`core/errors.py` 注册的
全局异常处理器就会把它变成统一格式：

```json
{ "code": 40003, "message": "PDF 中未检测到文字层……", "detail": null }
```

前端拿到后直接展示 `message`，按 `code` 判断错误类型。错误码含义清单在 `Plan.md §7`。

### 3.6 与大模型打交道的方式（agent/llm.py）

大模型只会输出文本，而我们需要**结构化数据**（比如画像 JSON）。本项目的做法：

```
提示词 + Pydantic 模型
  → 让模型只输出 JSON（把模型的 JSON Schema 附在提示词里）
  → json.loads 解析 → Pydantic 校验字段类型
  → 不合格？把具体错误信息拼进提示词再问一次
  → 还不合格？任务标 failed，前端提示可重试
```

这个流程封装在 `structured_generate()` 里，简历解析和项目分析都调它，不各写一套。

## 4. 前端是怎么跑起来的（Next.js 速成）

### 4.1 心智模型：页面 = 组件 = 函数

React 的核心思想：**界面是数据的函数**。`UI = f(state)`。

```tsx
// frontend/src/app/page.tsx（简化）
const [interviews, setInterviews] = useState<InterviewSummary[] | null>(null);
// ↑ state：组件自己的记忆。 interviews 变了 → 组件自动重新渲染

useEffect(() => { /* 挂载后去后端拉列表 */ load(); }, []);
// ↑ 副作用：页面出现后执行一次（类似"初始化"）

return interviews === null
  ? <p>加载中……</p>                                    // 数据没到：显示加载中
  : <ul>{interviews.map(i => <li key={i.id}>{i.status}</li>)}</ul>;  // 到了：渲染列表
```

不需要操作 DOM（没有 `document.getElementById` 这类东西），**改数据，界面自己变**。

### 4.2 文件夹即网址（App Router）

```
src/app/new/page.tsx      →  网址 /new
src/app/prepare/page.tsx  →  网址 /prepare
src/app/page.tsx          →  网址 /
```

想加页面：新建文件夹 + `page.tsx`，完事。

### 4.3 前后端唯一的桥：lib/api.ts

页面**从不直接写 fetch**，统一走封装：

```ts
await api<InterviewDetail>(`/interviews/${id}`);            // GET
await api(`/interviews/${id}/profile`, { method: "PUT", json: body });  // PUT + JSON
await apiUpload<InterviewCreated>("/interviews", formData); // 上传文件
```

`api()` 自动做三件事：带 `Authorization: Bearer <token>`（登录凭证存 localStorage）、
非 2xx 时抛带后端错误码的 `ApiError`、401 时清 token 踢回登录页。

### 4.4 数据类型：types/api.ts 与后端手工对齐

后端 `schemas.py` 里每个 Pydantic 模型，前端都有一个长得一样的 TypeScript interface：

```
后端 models/schemas.py          前端 types/api.ts
class ResumeProfile    ←手工同步→  interface ResumeProfile
```

TypeScript 是「带类型检查的 JavaScript」：字段名写错、把数字当字符串用，**编译期就报错**，
而不是运行时界面莫名空白。改了后端契约记得同步改这里（目前没有自动生成，靠自觉）。

### 4.5 为什么要轮询？/prepare 页的工作方式

解析要几十秒，HTTP 又不能挂几十秒等结果，所以前端做的是：

```
useEffect 起 setInterval，每 2s GET /interviews/{id}
  → 任务还在 pending/running：继续轮询
  → 变成 awaiting_confirm：停轮询，展示画像编辑表单
  → 变成 failed：停轮询，显示错误 + 「重试」按钮（点击后恢复轮询）
```

（P3 的面试对话会换成 SSE 流式推送，但准备页这种场景用轮询最简单可靠。）

## 5. 发布形态：为什么前端是「静态导出」

`next.config.ts` 里 `output: "export"`：`npm run build` 把所有页面**预渲染成纯 HTML/JS/CSS**
（`out/` 目录），`postbuild` 脚本自动拷到 `backend/static/`。FastAPI 直接把这些文件当静态资源托管。

好处：**部署只需要跑一个后端进程**——访问 `127.0.0.1:8000/` 时，FastAPI 优先返回接口 JSON，
其它路径返回前端页面（没匹配到就回退 `index.html`，即 SPA fallback）。

代价：没有 Node 服务器，所以不能用 `/interviews/123` 这种动态路由（构建时不知道 id），
一律改成查询参数 `/prepare?id=123`，页面里用 `useSearchParams()` 读取。

开发期则前后端分开跑：`npm run dev`（3000 端口）+ 后端（8000 端口），后端开了 CORS 放行 3000。

## 6. 本地开发的一天（操作手册）

```bash
# 一次性准备
#   1. MySQL 起好、建库 intervieweragent、配好 backend/.env（照 .env.example）
#   2. cd frontend && npm install

# ── 日常开发 ──────────────────────────────
# 终端 1：后端（改 Python 代码自动重启）
cd backend && uv run python -m app.main        # http://127.0.0.1:8000

# 终端 2：前端（改 TSX 代码热更新）
cd frontend && npm run dev                     # http://localhost:3000

# 浏览器开 http://localhost:3000 开发调试

# ── 验收 / 演示形态 ───────────────────────
cd frontend && npm run build                   # 静态导出 + 自动拷到 backend/static
# 之后只开后端，直接访问 http://127.0.0.1:8000

# ── 跑测试 ────────────────────────────────
uv run pytest                  # 全量（数据库相关用例连不上 MySQL 会自动 skip）
uv run pytest -k "not ping"    # 跳过真实调 LLM 的连通性测试
```

调试技巧：

- 后端日志看终端 1（谁注册了、哪个任务完成、哪里失败，都有 INFO/WARNING 日志；内容脱敏，不含简历原文和密钥）。
- 接口想直接看原始返回：浏览器或 curl 打 `http://127.0.0.1:8000/docs` —— FastAPI **自动生成的交互式接口文档**，能直接点 Try it out 调试每个接口。
- 前端报错看浏览器 F12 的 Console 和 Network 标签（Network 里能看到每个请求的 URL、状态码、返回 JSON）。
